WHY THE BILLBOARDS ARE INVISIBLE  (traced 2026-09-07)
═══════════════════════════════════════════════════════════════════════════
Instrumented demo_dungeon_room at the natural spawn (UW_ENABLE_TILE_FEATURES=1):

- FUN_00065394 is called for ~75 visible tiles; many have objects (tile
  (16,0) has 4). All objects at spawn are render class 0
  ((&DAT_00202c9a)[type*0xd] & 3 == 0): type 0x80 (the bag), 0xc1-0xd5,
  0x140, 0x177.
- FUN_00060aa0's class-0 branch runs for each: emits opcode 0x7a + screen
  X/Y/Z into DAT_00110fc0, calls FUN_00040770 to decode the sprite, then
  builds a 4-vertex quad into DAT_000a85d8[] and bumps the geom record
  count (DAT_000a85d4 / DAT_0023b83c).
- render_dungeon_view: geom records 70 (tiles only, OFF) -> 84 (ON), and
  near_clip_visible_tiles keeps 70 -> 80. So ~10 object quads DO reach
  render_visible_tile_list.
- render_visible_tile_list rasterises all 80. Screenshot ON == OFF
  byte-for-byte -> the 10 object quads draw NOTHING.

Root cause: the per-record texture pointer. render_visible_tile_list reads
`g_tile_texptr_out[record]` (the side channel added because the in-record
4-byte texture field truncates on 64-bit). process_visible_tile_cell writes
`g_tile_texptr_emit[DAT_0023b83c] = get_texture_page(...)` for tiles.
FUN_00060aa0 / FUN_00040770 do NOT write that side channel for objects, so
object records read a stale/tile texptr (or null) -> null-texture span ->
no pixels.

The obvious fix (publish FUN_00040770's decoded sprite buffer via
g_tile_texptr_emit[DAT_0023b83c]) does NOT work as-is: at FUN_00040770 time
DAT_0023b83c is small (observed 6, 19, 22, 29, 38, 45, 61) while the same
object record shows up in near_clip's list at emit-index 70+. So there are
(at least) two record counters that have diverged:
  DAT_0023b83c  -- bumped by process_visible_tile_cell AND FUN_00060aa0
  DAT_000a85d4  -- the count near_clip_visible_tiles iterates
FUN_00060aa0 keeps them "in sync" with `DAT_0023b83c = DAT_000a85d4 = X+1`
at the end of class 0/1, but the value seen mid-function is not the list
index. Need to pin down exactly which counter indexes the DAT_000a85d8[]
record that near_clip reads, and write g_tile_texptr_emit at THAT index
(and confirm near_clip's emit->out remap carries it).

Once the texptr is correct, also verify: object quad screen coords /
winding / size are sane (the class-0 path scales by DAT_00202508 x
DAT_002022f8 = sprite w x h and a -6/-4 * 0.5 offset), and depth ordering
vs tiles (painter's order -- objects emitted after tiles should draw on
top).

UPDATE 2026-09-11: THE RENDER-CLASS DISPATCH MECHANISM, PRECISELY
═══════════════════════════════════════════════════════════════════════════
This has come up enough times above ("render classes 1-3", "class-0 objects
render through the mesh list") that it's worth nailing down exactly what
decides which code path an object takes. Short answer: it is a static
per-object-*type* property table, NOT a function-pointer table -- a
different mechanism from the frame/mode dispatch tables this project found
hidden elsewhere (DAT_00085668, DAT_00085728, PTR_FUN_00087220 -- see
memory.md's "HOW WE GOT THE DISPATCH TABLES POPULATED"). Don't conflate the
two; this one really is just an if-chain reading a data field, confirmed
fresh from Ghidra, not a lost jump table.

THE TABLE: comobj.dat, loaded once at startup into DAT_00202c90 (uw.c
~41163-41184). 512 fixed records, one per object *type* ID (0x000-0x1ff),
indexed directly as `(&DAT_00202c9X)[type_id * 0xd]`. On disk each record
is 11 bytes; in memory the stride is 13 (0xd) bytes, so offsets 4 and 0xc
are real, permanent padding (confirmed: comobj.dat is exactly 512*11+2 =
5634 bytes; the loader's own read calls only ever touch 11 of the 13
bytes per iteration, uw.c ~41173-41181). This is a PER-TYPE table --
separate from each individual placed object's own live record (tile
position, heading, quality/flags), which is walked from each tile's object
chain and holds per-*instance* state. Rendering always needs both: the type
record says what KIND of thing this is and how to draw it; the instance
record says where.

THE DISPATCH FIELD: byte offset 0xa of the type record (DAT_00202c9a). Its
low 2 bits are the "render class" read at the top of emit_tile_objects
(was FUN_00060aa0), uw.c ~49659 (`bVar13 = (&DAT_00202c9a)[(id&0x1ff)*0xd]
& 3`):
  0 -- mesh/sprite billboard quad (LAB_emit_mesh_sprite_quad) -- the
       default path; ordinary items, the spawn sack, and (as of this
       session) the OLD boulder behavior before it got its own special
       case.
  1 -- critter: animated, direction-octant sprite via CRxxPAGE.Nxx +
       ASSOC.ANM (resolve_critter_sprite_tier / decode_critter_sprite_page).
  2 -- door / wall-sign -- both rerouted into the SAME class-0 quad path
       (`goto LAB_emit_mesh_sprite_quad`), split apart *inside* that branch
       by the object's own `id & 0x30` (door vs TMOBJ sign/plaque), not by
       anything in comobj.dat.
  3 -- light/quantity-flagged special billboards (torches, thrown-weapon /
       muzzle-flash effects) via emit_object_billboard(0x14 or 0x16, ...).
Bits 2-5 of this SAME byte are read elsewhere (uw.c:41305, `>>2 & 0xf`) for
an apparently unrelated purpose (looks light-radius-shaped) -- the byte is
multiplexed, "render class" is only ever its bottom two bits.

ONE FUNCTION, NOT SEVERAL: before touching any of this for the Models work
below, got a FRESH Ghidra decompile of the real emit_tile_objects
(FUN_00060aa0) specifically to check whether the class dispatch was secretly
a jump/function-pointer table Ghidra had collapsed into an if-chain (the
exact bug class DAT_00085668 turned out to be). It is not -- the real
binary's dispatch is a genuine, exhaustive 2-bit if/else, matching our
recovered uw.c exactly, no drift from past sessions' editing. So in this
codebase, "different object types get dispatched to different render
functions" really means: ONE function, called once per object as each
visible tile's chain is walked, branching internally on this 2-bit field,
with FURTHER hardcoded object-ID special cases layered inside each branch
on top of that (id 0x160-0x16f == TMOBJ signs; id & 0x30 == door vs sign;
id 0x153-0x156 == boulder-model lookup, added this session, see below).
There is no clean single table that fully answers "what renders this
object" -- it's the comobj.dat class byte PLUS a growing pile of id-range
checks hardcoded directly in emit_tile_objects.

THE NEGATIVE FINDING THAT MATTERS MOST: this 2-bit field tops out at 4
values, and there is no 5th "true 3D model" case anywhere in this Pocket PC
build -- not a lost/masked bit, genuinely absent (see the Models
investigation below, which checked this thoroughly rather than assuming
it). Whatever mechanism the original PC version may have used to select
real vertex-model objects, this WinCE port's object dispatch never had
that case; everything funnels into one of the four billboard-shaped paths
above. Reviving true 3D model rendering therefore could not be "find the
dropped case" -- it required bolting on a brand new object-id special case
that intercepts specific IDs before this dispatch even runs.

DUE DILIGENCE BEFORE BUILDING ANYTHING NEW: data/DATA3D/*.E holds 29 real
3D-model files (text format: BEGIN/POINTS/PARTS/.../END), already parsed at
startup by FUN_00038680 (uw.c ~24980) calling FUN_00020a74 (uw.c ~13195)
into 29 persistent buffers (DAT_00114c1c..DAT_0017e0ec) -- but nothing in
this decompile ever read them afterward. Rather than assume "dead code,
build a renderer from scratch," did the same due diligence this project's
history says to do for suspiciously-dead data (see the DAT_00085668 writeup
in memory.md): a real Ghidra reference search against UU.exe found ZERO
consumers of any of the 29 buffer addresses anywhere in the binary except
the loader (InspectModelBuffers.java, scratchpad); a raw-byte-pattern scan
across every initialized memory block for those same 29 addresses (in case
a compile-time pointer table held them without a Ghidra-recognized
reference -- the exact DAT_00085668 bug class) found nothing
(FindPointerTables.java); a full .text undefined-byte-gap scan found zero
gaps larger than 16 bytes anywhere in the executable region, so there's no
room for an undiscovered consumer function either (CheckUndefinedGaps.java);
the fresh emit_tile_objects decompile above ruled out a collapsed dispatch
case; and comobj.dat's loader (see the dispatch writeup above) confirmed
its "extra" padding bytes are real padding, not a dropped model-index
field. CONCLUSION, checked rather than assumed: this Pocket PC port shipped
the model loader but never wired a renderer to it. Reviving it meant
writing a real consumer, not unstubbing a hidden one.

A REAL BUG FOUND ALONG THE WAY: while instrumenting the loaded buffers
(UW_DUMP_MODEL_RAW=1) to reverse-engineer the output format, every parsed
point's first float came out as a constant 3.0 while Y/Z matched the
source .E text exactly. Root cause: FUN_00020a74's POINTS-parsing loop
calls Ordinal_2032() (int->float) for X with the argument dropped, while
the next two lines convert Y and Z correctly -- the same "dropped
argument, ARM register-leftover idiom doesn't survive a literal recompile"
bug class as everywhere else in this file, just never caught before
because nothing consumed the output. Fixed (uw.c ~13427). This had been
silently corrupting the X coordinate of every point in all 29 loaded
models the whole time, independent of whether a renderer existed.

FUN_00020a74's OUTPUT BUFFER LAYOUT (recovered empirically, by dumping and
diffing against the real .E text, after the X-coordinate fix): offset 0 =
point count (int); offset 4 = part count (int, with an occasional spurious
trailing 1-vertex entry -- filtered by requiring 3 <= vcount <= 4); points
at `8 + i*0xc` as 3 back-to-back little-endian floats (X, Y-up, Z-depth,
matching the .E file's own axis order); parts at `0xc14 + p*0x60`: a vertex
count (int) then that many vertex-index ints (into the points array)
starting at `+4`.

THE RENDERER: emit_model_object (new, uw.c, just above emit_tile_objects)
pushes each model FACE as its own record into the shared
DAT_000a85d0_backing arena (doc comment ~uw.c:116) that tile wall/floor
geometry already uses, and lets the EXISTING
translate_verts_to_camera_space / project_verts_through_view_matrix /
near_clip_visible_tiles / render_visible_tile_list pipeline do real
per-vertex 3D transform and N-gon-fan rasterization -- confirmed
render_visible_tile_list was already generic over a record's point count,
not hardcoded to 4 (quads), so this needed zero rasterizer changes. This
reuses the real 3D transform pipeline rather than extending the
class-0 quad path's screen-space billboard-extrusion trick (which only
ever places one flat rectangle around an already-projected 2D anchor, and
would not have given genuine per-vertex 3D projection at different
distances/angles).

Model points are rotated by the object's heading (0-7, 45-degree steps)
and added to the object's already-computed world anchor (DAT_0023b904/
91c/920 -- despite being printed as "scrx/scry/scrz" by an earlier debug
hook, these are pre-translate WORLD-ish coordinates in the same
256-units/tile scale as tile geometry, not final screen pixels) in the
same (X, height, depth) field order process_visible_tile_cell uses for
real tile vertices. UW_MODEL_SCALE (default 8.0) converts the model's
small local .E units (a rock spans roughly -18..24) into that world scale.
Faces render texture-less (texptr left 0, a flat constant shade) rather
than solving real UV/material mapping in this pass -- see "LAST GAP" above
(the still-open 2D-sprite UV problem) and Open below; both need the same
fix eventually.

Object-id -> model lookup (lookup_boulder_model, small switch, same shape
as the existing door/sign id-based special-casing in emit_tile_objects's
class-2 branch): 0x156 "a_small boulder" -> ROCKSMAL, 0x155 "a_boulder" ->
ROCKMED, 0x153/0x154 "a_large boulder" -> ROCKBIG. No id->model field
exists anywhere in comobj.dat or the binary (see due diligence above) --
this is a hand-built table, not a recovered one, intercepted at the very
top of emit_tile_objects (right after the object id is read) so boulders
skip the normal render-class dispatch entirely. UW_DISABLE_MODEL_RENDER=1
reverts to the old billboard-quad behavior for comparison.

UPDATE 2026-09-11 (4): MODELS ALSO NEEDED A 45-DEGREE STEP, BUT THE OPPOSITE SIGN FROM SIGNS/DOORS
═══════════════════════════════════════════════════════════════════════════
User question: "does the model heading need the same +1 compass-step fix
signs/doors needed?" Good instinct -- yes, but the sign was wrong to
assume it'd be the SAME correction.

The sign/door billboard-angle-override code (uw.c ~50670-50680) applies
`((quadrant_heading + 1) & 7) * 45` -- a "+1 compass step" on top of the
quadrant compensation, confirmed live in that code's own comment ("45
degrees off from flush -- one compass step correction"). Assumed at
first this would carry over unchanged to the new 3D model code. Tested
it properly instead of assuming: added a temporary UW_MODEL_HEADING_

all 8 possible compass-step offsets (-3 through +2 tested explicitly,

the doorway, matching the surrounding wall geometry exactly.

So the correction is real (confirms the user's instinct), but its SIGN
is the opposite of the billboard code's +1 -- makes sense once you
think about WHY: the billboard code rotates a 2D quad-extension
direction through a sin/cos LOOKUP TABLE (DAT_000d9ed8/DAT_000d9930),
while this session's model code applies a real rotation MATRIX
(cos/sin computed directly) to actual 3D model-space vertices. Those
are two different rotation conventions/senses that happen to share the
same underlying "quadrant compensation" need but not the same fixed
offset on top of it -- porting the sign code's exact constant without
re-testing would have been wrong. Baked in as the new default (`_step =
-1` in the model heading block, uw.c, right after the quadrant
compensation), with UW_MODEL_HEADING_OFFSET still available as an
override for future tuning. Boulder and bridge regression-checked with
the new default -- both still render as plausible, undistorted shapes
(expected: boulder is asymmetric so any rotation looks like "a rock";
bridge's own heading happened to not visibly change orientation at its
repro spot).

Tried to also confirm on a second, independently-placed door (tile 9,10,
a different raw stored heading than the repro door) as a generalization
check -- inconclusive, not a contradiction: the debug log showed multiple
different raw heading values for "the same" id 0x140 within one static
demo run, which is more likely 2+ separate door objects in view at that
busier corridor position (not tracked apart in the quick test) than a
real per-frame heading change, and no obvious door silhouette was visible
in that screenshot at all (possibly occluded/edge-on from that specific
stance). Given the first test's result was unambiguous across a clean,

chasing a messier second repro -- but this is the natural next thing to
verify if a differently-oriented door ever looks wrong.

function (collision_height_envelope, uw.c ~40537) both only ever compute
FLOOR height from per-tile/per-corner data; the "ceiling clearance"
concept that does exist (_DAT_0008699f, reticle_object_pick) is a
movement/physics headroom check seeded from a large sentinel (0x7f) and
narrowed only by specific nearby overhead objects, not a per-tile
geometry field. Cross-checked against this project's own earlier tile-
rendering investigation (memory.md, UPDATE 18): "UW1's ceiling is a fixed

solid rock 128" in a raw sub-unit scale. No per-tile ceiling HEIGHT field

═══════════════════════════════════════════════════════════════════════════
Next-work ask: "use the object's sprite as the door model texture; use
the tile's wall texture as the frame model's texture." Wired both up
using the exact mechanisms already proven correct elsewhere in this file
-- got real, valid texture data into the pipeline for both -- but NEITHER
produces visible texture detail on screen. This section is a full record
of what was tried and what was learned, because the actual blocker turned
out to be much deeper than "wire up a texture pointer."

WHAT WAS BUILT:
- emit_model_object gained a `texptr` parameter. Each record it creates
  now publishes through g_tile_texptr_emit[rec] (the same side-channel
  array every other texture consumer in this file already uses to work
  around the in-record field truncating a 64-bit pointer to 4 bytes) --
  texptr==0 keeps the old flat-shaded fallback unchanged.
- LEAF (door): reused the closed-door billboard branch's own already-
  correct sprite frame formula, `DAT_00202734 + (raw_type_word & 7) +
  0x30`, fed through FUN_00040770 (the same real sprite decoder the 2D
  billboard path uses) to decode it, then captured the resulting buffer
  from g_tile_texptr_emit[DAT_0023b83c] right after the call (rather than
  relying on index timing) so it could be stamped onto every record the
  leaf's several faces create, not just one.
- FRAME (door): found the tile's OWN real wall-texture index by reading
  DAT_0023b4ec[2] & 0x3f (DAT_0023b4ec is the raw tile record currently
  being walked; this exact field is documented a few hundred lines above
  emit_tile_objects, in the tile-wall-rendering code itself: "UW1 tile
  word2 (bytes 2-3) bits 0-5 = wall texture index"), added 0x3a (the same
  offset that same wall-rendering code adds before calling
  get_texture_page() for the 16x16 wall-sized arena slot specifically, as
  opposed to the unmodified value used for the 64x64 floor/ceiling case),
  and called get_texture_page() with it -- the identical call the real
  wall renderer makes for this exact tile.

BOTH TEXTURE POINTERS ARE GENUINELY VALID. Added a debug pixel-histogram
check (same technique the critter sprite decoder's own UW_DEBUG_CRITTER
hook already used) -- the leaf's decoded sprite came back 1408/2048
nonzero pixels, a real 32x64 door graphic, not garbage or an empty
buffer. The frame's wall texture pointer resolved to a real, non-null
get_texture_page() result too.

RESULT: applying the leaf's sprite texture made the leaf DISAPPEAR
entirely (worse than flat-shaded) -- consistent with object-rendering-
findings.txt's own much older "LAST GAP" finding (top of this file, from
the original 2D sprite-billboard work): render_visible_tile_list derives
each vertex's texture-sample coordinate from its PROJECTED SCREEN
POSITION (near_clip_visible_tiles, offsets +0x3008/+0x300c off a per-
vertex projected-coordinate cache), not a real per-vertex UV. That
happens to look fine for a large, continuously-tiling WALL texture
(screen position lands somewhere valid no matter what), but a small
finite sprite bitmap mostly samples outside its own bounds -> reads as
transparent -> the whole leaf vanishes. This is the SAME root cause the
2D billboard sprite path has always had, just newly confirmed to affect
3D models too, since they ride the identical rendering pipeline. Reverted
to opt-in only (UW_MODEL_LEAF_TEXTURE=1); default stays untextured
(unchanged from before this session's texture work).

Applying the frame's wall texture did NOT make it disappear (a wall
texture is large enough that screen-position sampling always lands
somewhere valid) -- but it also didn't show any real texture DETAIL: a
zoomed crop of the rendered header and leaf both show perfectly flat,
uniform color, no brick/stone graining at all, before and after the
texture was applied. Chased one specific lead: real wall-rendering code
(uw.c ~49025-49032, literally the block right before emit_tile_objects
in this same function) writes the texture's tile size (DAT_0023b824 --
16 for walls, 64 for floor/ceiling) into two record fields (rb+0x0,
rb+0x4) that emit_model_object was unconditionally zeroing. Fixed that
(now writes 16 for any textured record) -- no visible change. Went one
step further and read the SAME wall-rendering code's actual raw-VERTEX
writes (uw.c ~49048-49060) expecting to confirm the vertex's 2nd/3rd
float fields are plain world Y/Z (what emit_model_object assumes and
what already works correctly for position) -- they are NOT, for walls:
those fields are computed as `Ordinal_2032((position + DAT_00086bb0/
bb1[wall_segment_index]) * 0x100)`, blending the position with a texture-
repeat lookup table indexed by which wall segment this is. Wall geometry
has its OWN specialized vertex-encoding scheme with texture-tiling baked
directly into the position fields via that table -- it is not a generic
"any 3D triangle can be textured this way" mechanism, and does not appear
to generalize to arbitrary-oriented model geometry (which needs its raw
X/Y/Z to stay literal world coordinates for POSITION to keep working,
which it does, confirmed by every model screenshot in this file).

CONCLUSION: texturing arbitrary 3D model geometry in this renderer is a
substantially deeper problem than "find the right texture pointer and
publish it" -- every existing texture consumer in this codebase (tile
walls, floor/ceiling, 2D object billboards) is tightly special-cased to
its own geometry shape, and none of those special cases were built to
generalize. Solving it for real would mean reverse-engineering how
near_clip_visible_tiles' projected-coordinate cache (+0x3008/+0x300c)
actually turns into a texture sample for the RASTERIZER'S span-drawing
code (not yet traced this session), likely requiring either a genuinely
new per-vertex UV field nothing currently writes, or replicating wall
geometry's position/texture-blending trick for a rotated model (which
doesn't obviously make sense for non-axis-aligned surfaces). This is
project-sized work on the same order as the original "get 3D models
rendering at all" investigation, not a small follow-up -- flagging
clearly rather than continuing to guess-and-check further this session.

CURRENT STATE: the frame's wall-texture wiring is left ACTIVE (harmless
-- visually identical to the untextured flat-shade fallback it already
had, and the plumbing -- g_tile_texptr_emit publishing, the texsize
field fix -- is real, correct infrastructure worth keeping even though
it doesn't yet produce a visible result). The leaf's sprite-texture
wiring is left build-time-present but OPT-IN via UW_MODEL_LEAF_
TEXTURE=1 (default off), because applying it actively regresses (leaf
disappears) rather than merely failing to improve.

UPDATE 2026-09-11 (7): THE .E PARSER COMPUTES A REAL FACE NORMAL -- AND THROWS IT AWAY
═══════════════════════════════════════════════════════════════════════════
Traced parse_e_model_file (was FUN_00020a74) end to end looking for
per-face normal data, prompted by the texturing dead-end above. Right
after reading each PARTS entry's vertex-index list, the parser calls:

    vec3_sub(P[v0], P[v1], edge1);    // was FUN_000137c0
    vec3_sub(P[v0], P[v2], edge2);
    vec3_cross(edge2, edge1, normal); // was FUN_00013904, real cross product

confirmed via the exact formula each helper computes (vec3_sub =
elementwise param_2-param_1; vec3_cross = the textbook 3-float cross
product, including the Y term's required sign flip) -- a genuine,
deliberate per-face normal computation, not a coincidence.

That result is never referenced again anywhere in the function. To rule
out a dropped-store decompile bug (this project's most common bug class),
pulled the REAL ARM disassembly from UU.exe at the call site
(0x00021aa4): `bl 0x00013904` is immediately followed by unrelated
vertex-count bookkeeping (`ldr r3,[sp,#0x38]; cmp r3,#0x4...`), no store
of the result anywhere in between. This is the real shipped binary, not
a decompile artifact -- the original game computes this normal and then
genuinely never uses it. There is no per-face normal data anywhere in
the final parsed model buffer emit_model_object reads from.

Separately confirmed while in there: the existing shading pipeline has
no per-face-normal concept to plug one into anyway -- every writer of the
render record's shade byte across this whole file (tile walls, floors,
doors, signs, emit_model_object) pulls from one shared ambient/light-
proximity global (DAT_000da47c), never anything geometry-derived. Real
per-face lighting variation would be new behavior, not a gap-fill.

UPDATE 2026-09-11 (8): NO UV DATA EITHER -- THE FORMAT WAS NEVER TEXTURE-MAPPED
═══════════════════════════════════════════════════════════════════════════
Same investigation, extended to UV/texture coordinates (the direct
follow-up to UPDATE (6)'s texturing dead-end). Read the rest of
parse_e_model_file (PARTS through EXTENDED_COLORS/CLUSTERS/NODES/ANIMATE
and its final cleanup pass) end to end. Conclusion: no UV data exists
anywhere, in the file format or the parser -- more clear-cut than the
normal, which was at least computed.

- The .E format's only blocks, across every model file in DATA3D/: BEGIN/
  VERSION/NAMES/POINTS/PARTS/CLUSTERS/NODES/EXTENDED_COLORS/SCALE_SHIFT/
  END. No UV/TEXCOORD/MAPPING block anywhere.
- Each PARTS line has exactly 4 header fields before the vertex-index
  list: a flag (always 0 in every real file -- a `local_23c==4` "got
  bitmap" branch exists for a nonzero flag but is dead in practice),
  a 1-character code, a sequential part index, and a color value. No room
  for texture coordinates. The 1-character code is NOT UV-related either
  -- confirmed via the parser's own debug string: 'A' triggers a "making
  backside of %d %d" branch that duplicates a face with reversed winding
  (a double-sided-face flag), 'N' is the ordinary default. ('F'/'X' are
  two more recognized codes seen earlier in the function, for reversed
  vertex order and an unused "explicit bitmap" escape hatch respectively
  -- also not UV.)
- Went further than the normal check: even per-face COLOR -- both the raw
  hex material index and the EXTENDED_COLORS RGB entry (matched against
  g_model_known_ext_colors, was DAT_00084678, a 32-entry known-RGB table)
  -- suffers the identical fate as the normal. Traced the function's
  literal last operation before it returns (a scratch-to-scratch color-
  inheritance pass for parts that share a color with another part,
  gated by DAT_000db494) -- it writes back into scratch memory, never
  into the final output buffer. The only things that survive into what
  emit_model_object actually reads are point positions and each part's
  vertex-index list; normal, color, and (never-attempted) UV are all
  absent from the persisted model data.

Reframes the UPDATE (6) texturing dead-end: this was very likely never a
texture-mapped format to begin with. Its real design intent looks like
flat-per-face color (refined by the EXTENDED_COLORS palette-index

bitmap UV mapping. That's consistent with why chasing a UV system for it
hit a wall -- there was never one to find, not a bug to fix.
