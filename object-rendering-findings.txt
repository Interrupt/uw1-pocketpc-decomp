WHY THE BILLBOARDS ARE INVISIBLE  (traced 2026-09-07)
═══════════════════════════════════════════════════════════════════════════
Instrumented demo_dungeon_room at the natural spawn (UW_ENABLE_TILE_FEATURES=1):

- FUN_00065394 is called for ~75 visible tiles; many have objects (tile
  (16,0) has 4). All objects at spawn are render class 0
  ((&DAT_00202c9a)[type*0xd] & 3 == 0): type 0x80 (the bag), 0xc1-0xd5,
  0x140, 0x177.
- FUN_00060aa0's class-0 branch runs for each: emits opcode 0x7a + screen
  X/Y/Z into DAT_00110fc0, calls FUN_00040770 to decode the sprite, then
  builds a 4-vertex quad into DAT_000a85d8[] and bumps the geom record
  count (DAT_000a85d4 / DAT_0023b83c).
- render_dungeon_view: geom records 70 (tiles only, OFF) -> 84 (ON), and
  near_clip_visible_tiles keeps 70 -> 80. So ~10 object quads DO reach
  render_visible_tile_list.
- render_visible_tile_list rasterises all 80. Screenshot ON == OFF
  byte-for-byte -> the 10 object quads draw NOTHING.

Root cause: the per-record texture pointer. render_visible_tile_list reads
`g_tile_texptr_out[record]` (the side channel added because the in-record
4-byte texture field truncates on 64-bit). process_visible_tile_cell writes
`g_tile_texptr_emit[DAT_0023b83c] = get_texture_page(...)` for tiles.
FUN_00060aa0 / FUN_00040770 do NOT write that side channel for objects, so
object records read a stale/tile texptr (or null) -> null-texture span ->
no pixels.

The obvious fix (publish FUN_00040770's decoded sprite buffer via
g_tile_texptr_emit[DAT_0023b83c]) does NOT work as-is: at FUN_00040770 time
DAT_0023b83c is small (observed 6, 19, 22, 29, 38, 45, 61) while the same
object record shows up in near_clip's list at emit-index 70+. So there are
(at least) two record counters that have diverged:
  DAT_0023b83c  -- bumped by process_visible_tile_cell AND FUN_00060aa0
  DAT_000a85d4  -- the count near_clip_visible_tiles iterates
FUN_00060aa0 keeps them "in sync" with `DAT_0023b83c = DAT_000a85d4 = X+1`
at the end of class 0/1, but the value seen mid-function is not the list
index. Need to pin down exactly which counter indexes the DAT_000a85d8[]
record that near_clip reads, and write g_tile_texptr_emit at THAT index
(and confirm near_clip's emit->out remap carries it).

Once the texptr is correct, also verify: object quad screen coords /
winding / size are sane (the class-0 path scales by DAT_00202508 x
DAT_002022f8 = sprite w x h and a -6/-4 * 0.5 offset), and depth ordering
vs tiles (painter's order -- objects emitted after tiles should draw on
top).

UPDATE 2026-09-11: THE RENDER-CLASS DISPATCH MECHANISM, PRECISELY
═══════════════════════════════════════════════════════════════════════════
This has come up enough times above ("render classes 1-3", "class-0 objects
render through the mesh list") that it's worth nailing down exactly what
decides which code path an object takes. Short answer: it is a static
per-object-*type* property table, NOT a function-pointer table -- a
different mechanism from the frame/mode dispatch tables this project found
hidden elsewhere (DAT_00085668, DAT_00085728, PTR_FUN_00087220 -- see
memory.md's "HOW WE GOT THE DISPATCH TABLES POPULATED"). Don't conflate the
two; this one really is just an if-chain reading a data field, confirmed
fresh from Ghidra, not a lost jump table.

THE TABLE: comobj.dat, loaded once at startup into DAT_00202c90 (uw.c
~41163-41184). 512 fixed records, one per object *type* ID (0x000-0x1ff),
indexed directly as `(&DAT_00202c9X)[type_id * 0xd]`. On disk each record
is 11 bytes; in memory the stride is 13 (0xd) bytes, so offsets 4 and 0xc
are real, permanent padding (confirmed: comobj.dat is exactly 512*11+2 =
5634 bytes; the loader's own read calls only ever touch 11 of the 13
bytes per iteration, uw.c ~41173-41181). This is a PER-TYPE table --
separate from each individual placed object's own live record (tile
position, heading, quality/flags), which is walked from each tile's object
chain and holds per-*instance* state. Rendering always needs both: the type
record says what KIND of thing this is and how to draw it; the instance
record says where.

THE DISPATCH FIELD: byte offset 0xa of the type record (DAT_00202c9a). Its
low 2 bits are the "render class" read at the top of emit_tile_objects
(was FUN_00060aa0), uw.c ~49659 (`bVar13 = (&DAT_00202c9a)[(id&0x1ff)*0xd]
& 3`):
  0 -- mesh/sprite billboard quad (LAB_emit_mesh_sprite_quad) -- the
       default path; ordinary items, the spawn sack, and (as of this
       session) the OLD boulder behavior before it got its own special
       case.
  1 -- critter: animated, direction-octant sprite via CRxxPAGE.Nxx +
       ASSOC.ANM (resolve_critter_sprite_tier / decode_critter_sprite_page).
  2 -- door / wall-sign -- both rerouted into the SAME class-0 quad path
       (`goto LAB_emit_mesh_sprite_quad`), split apart *inside* that branch
       by the object's own `id & 0x30` (door vs TMOBJ sign/plaque), not by
       anything in comobj.dat.
  3 -- light/quantity-flagged special billboards (torches, thrown-weapon /
       muzzle-flash effects) via emit_object_billboard(0x14 or 0x16, ...).
Bits 2-5 of this SAME byte are read elsewhere (uw.c:41305, `>>2 & 0xf`) for
an apparently unrelated purpose (looks light-radius-shaped) -- the byte is
multiplexed, "render class" is only ever its bottom two bits.

ONE FUNCTION, NOT SEVERAL: before touching any of this for the Models work
below, got a FRESH Ghidra decompile of the real emit_tile_objects
(FUN_00060aa0) specifically to check whether the class dispatch was secretly
a jump/function-pointer table Ghidra had collapsed into an if-chain (the
exact bug class DAT_00085668 turned out to be). It is not -- the real
binary's dispatch is a genuine, exhaustive 2-bit if/else, matching our
recovered uw.c exactly, no drift from past sessions' editing. So in this
codebase, "different object types get dispatched to different render
functions" really means: ONE function, called once per object as each
visible tile's chain is walked, branching internally on this 2-bit field,
with FURTHER hardcoded object-ID special cases layered inside each branch
on top of that (id 0x160-0x16f == TMOBJ signs; id & 0x30 == door vs sign;
id 0x153-0x156 == boulder-model lookup, added this session, see below).
There is no clean single table that fully answers "what renders this
object" -- it's the comobj.dat class byte PLUS a growing pile of id-range
checks hardcoded directly in emit_tile_objects.

THE NEGATIVE FINDING THAT MATTERS MOST: this 2-bit field tops out at 4
values, and there is no 5th "true 3D model" case anywhere in this Pocket PC
build -- not a lost/masked bit, genuinely absent (see the Models
investigation below, which checked this thoroughly rather than assuming
it). Whatever mechanism the original PC version may have used to select
real vertex-model objects, this WinCE port's object dispatch never had
that case; everything funnels into one of the four billboard-shaped paths
above. Reviving true 3D model rendering therefore could not be "find the
dropped case" -- it required bolting on a brand new object-id special case
that intercepts specific IDs before this dispatch even runs.

DUE DILIGENCE BEFORE BUILDING ANYTHING NEW: data/DATA3D/*.E holds 29 real
3D-model files (text format: BEGIN/POINTS/PARTS/.../END), already parsed at
startup by FUN_00038680 (uw.c ~24980) calling FUN_00020a74 (uw.c ~13195)
into 29 persistent buffers (DAT_00114c1c..DAT_0017e0ec) -- but nothing in
this decompile ever read them afterward. Rather than assume "dead code,
build a renderer from scratch," did the same due diligence this project's
history says to do for suspiciously-dead data (see the DAT_00085668 writeup
in memory.md): a real Ghidra reference search against UU.exe found ZERO
consumers of any of the 29 buffer addresses anywhere in the binary except
the loader (InspectModelBuffers.java, scratchpad); a raw-byte-pattern scan
across every initialized memory block for those same 29 addresses (in case
a compile-time pointer table held them without a Ghidra-recognized
reference -- the exact DAT_00085668 bug class) found nothing
(FindPointerTables.java); a full .text undefined-byte-gap scan found zero
gaps larger than 16 bytes anywhere in the executable region, so there's no
room for an undiscovered consumer function either (CheckUndefinedGaps.java);
the fresh emit_tile_objects decompile above ruled out a collapsed dispatch
case; and comobj.dat's loader (see the dispatch writeup above) confirmed
its "extra" padding bytes are real padding, not a dropped model-index
field. CONCLUSION, checked rather than assumed: this Pocket PC port shipped
the model loader but never wired a renderer to it. Reviving it meant
writing a real consumer, not unstubbing a hidden one.

A REAL BUG FOUND ALONG THE WAY: while instrumenting the loaded buffers
(UW_DUMP_MODEL_RAW=1) to reverse-engineer the output format, every parsed
point's first float came out as a constant 3.0 while Y/Z matched the
source .E text exactly. Root cause: FUN_00020a74's POINTS-parsing loop
calls Ordinal_2032() (int->float) for X with the argument dropped, while
the next two lines convert Y and Z correctly -- the same "dropped
argument, ARM register-leftover idiom doesn't survive a literal recompile"
bug class as everywhere else in this file, just never caught before
because nothing consumed the output. Fixed (uw.c ~13427). This had been
silently corrupting the X coordinate of every point in all 29 loaded
models the whole time, independent of whether a renderer existed.

FUN_00020a74's OUTPUT BUFFER LAYOUT (recovered empirically, by dumping and
diffing against the real .E text, after the X-coordinate fix): offset 0 =
point count (int); offset 4 = part count (int, with an occasional spurious
trailing 1-vertex entry -- filtered by requiring 3 <= vcount <= 4); points
at `8 + i*0xc` as 3 back-to-back little-endian floats (X, Y-up, Z-depth,
matching the .E file's own axis order); parts at `0xc14 + p*0x60`: a vertex
count (int) then that many vertex-index ints (into the points array)
starting at `+4`.

THE RENDERER: emit_model_object (new, uw.c, just above emit_tile_objects)
pushes each model FACE as its own record into the shared
DAT_000a85d0_backing arena (doc comment ~uw.c:116) that tile wall/floor
geometry already uses, and lets the EXISTING
translate_verts_to_camera_space / project_verts_through_view_matrix /
near_clip_visible_tiles / render_visible_tile_list pipeline do real
per-vertex 3D transform and N-gon-fan rasterization -- confirmed
render_visible_tile_list was already generic over a record's point count,
not hardcoded to 4 (quads), so this needed zero rasterizer changes. This
reuses the real 3D transform pipeline rather than extending the
class-0 quad path's screen-space billboard-extrusion trick (which only
ever places one flat rectangle around an already-projected 2D anchor, and
would not have given genuine per-vertex 3D projection at different
distances/angles).

Model points are rotated by the object's heading (0-7, 45-degree steps)
and added to the object's already-computed world anchor (DAT_0023b904/
91c/920 -- despite being printed as "scrx/scry/scrz" by an earlier debug
hook, these are pre-translate WORLD-ish coordinates in the same
256-units/tile scale as tile geometry, not final screen pixels) in the
same (X, height, depth) field order process_visible_tile_cell uses for
real tile vertices. UW_MODEL_SCALE (default 8.0) converts the model's
small local .E units (a rock spans roughly -18..24) into that world scale.
Faces render texture-less (texptr left 0, a flat constant shade) rather
than solving real UV/material mapping in this pass -- see "LAST GAP" above
(the still-open 2D-sprite UV problem) and Open below; both need the same
fix eventually.

Object-id -> model lookup (lookup_boulder_model, small switch, same shape
as the existing door/sign id-based special-casing in emit_tile_objects's
class-2 branch): 0x156 "a_small boulder" -> ROCKSMAL, 0x155 "a_boulder" ->
ROCKMED, 0x153/0x154 "a_large boulder" -> ROCKBIG. No id->model field
exists anywhere in comobj.dat or the binary (see due diligence above) --
this is a hand-built table, not a recovered one, intercepted at the very
top of emit_tile_objects (right after the object id is read) so boulders
skip the normal render-class dispatch entirely. UW_DISABLE_MODEL_RENDER=1
reverts to the old billboard-quad behavior for comparison.

═══════════════════════════════════════════════════════════════════════════

UPDATE 2026-09-11 (4): MODELS ALSO NEEDED A 45-DEGREE STEP, BUT THE OPPOSITE SIGN FROM SIGNS/DOORS
═══════════════════════════════════════════════════════════════════════════
User question: "does the model heading need the same +1 compass-step fix
signs/doors needed?" Good instinct -- yes, but the sign was wrong to
assume it'd be the SAME correction.

The sign/door billboard-angle-override code (uw.c ~50670-50680) applies
`((quadrant_heading + 1) & 7) * 45` -- a "+1 compass step" on top of the
quadrant compensation, confirmed live in that code's own comment ("45
degrees off from flush -- one compass step correction"). Assumed at
first this would carry over unchanged to the new 3D model code. Tested
it properly instead of assuming: added a temporary UW_MODEL_HEADING_
OFFSET env override and screenshotted the door repro (tile 24,7) across
all 8 possible compass-step offsets (-3 through +2 tested explicitly,
the rest by symmetry). Result: offset 0 and +1 (the sign/door value)

the ONLY offset that produced a clean, axis-aligned rectangle flush with
the doorway, matching the surrounding wall geometry exactly.

So the correction is real (confirms the user's instinct), but its SIGN
is the opposite of the billboard code's +1 -- makes sense once you
think about WHY: the billboard code rotates a 2D quad-extension
direction through a sin/cos LOOKUP TABLE (DAT_000d9ed8/DAT_000d9930),
while this session's model code applies a real rotation MATRIX
(cos/sin computed directly) to actual 3D model-space vertices. Those
are two different rotation conventions/senses that happen to share the
same underlying "quadrant compensation" need but not the same fixed
offset on top of it -- porting the sign code's exact constant without
re-testing would have been wrong. Baked in as the new default (`_step =
-1` in the model heading block, uw.c, right after the quadrant
compensation), with UW_MODEL_HEADING_OFFSET still available as an
override for future tuning. Boulder and bridge regression-checked with
the new default -- both still render as plausible, undistorted shapes
(expected: boulder is asymmetric so any rotation looks like "a rock";
bridge's own heading happened to not visibly change orientation at its
repro spot).

Tried to also confirm on a second, independently-placed door (tile 9,10,
a different raw stored heading than the repro door) as a generalization
check -- inconclusive, not a contradiction: the debug log showed multiple
different raw heading values for "the same" id 0x140 within one static
demo run, which is more likely 2+ separate door objects in view at that
busier corridor position (not tracked apart in the quick test) than a
real per-frame heading change, and no obvious door silhouette was visible
in that screenshot at all (possibly occluded/edge-on from that specific
stance). Given the first test's result was unambiguous across a clean,
isolated single-object sweep, treated that as sufficient rather than
chasing a messier second repro -- but this is the natural next thing to
verify if a differently-oriented door ever looks wrong.

parts loop. Safe per-vertex here because DFRAME.E's Y=1024 points aren't
shared with any other, correctly-sized part. Result: emitted face count

the opening with the passage clearly open below it, not two floating

300 guess from UPDATE (2). Looked for a real per-tile ceiling-height field

(collision_sample_floor_height, uw.c ~39962) and the tile-height envelope
function (collision_height_envelope, uw.c ~40537) both only ever compute
FLOOR height from per-tile/per-corner data; the "ceiling clearance"
concept that does exist (_DAT_0008699f, reticle_object_pick) is a
movement/physics headroom check seeded from a large sentinel (0x7f) and
narrowed only by specific nearby overhead objects, not a per-tile
geometry field. Cross-checked against this project's own earlier tile-
rendering investigation (memory.md, UPDATE 18): "UW1's ceiling is a fixed
per-level texture, no per-tile ceiling bits" -- and the same investigation's
collision work found floor-height bytes read per-tile as "open ~80-96,
solid rock 128" in a raw sub-unit scale. No per-tile ceiling HEIGHT field
exists anywhere in this decompile to read -- matches the texture finding
that ceilings aren't a per-tile geometry concept in this game's format at
all, presumably a uniform one-slab-per-level height instead.

per-tile lookup, since no such field was found -- a genuinely tall or
multi-level room would still cap short at this height; worth revisiting

UPDATE 2026-09-11 (6): TEXTURING MODELS -- REAL TEXTURE DATA, ZERO VISIBLE DETAIL
═══════════════════════════════════════════════════════════════════════════
Next-work ask: "use the object's sprite as the door model texture; use
the tile's wall texture as the frame model's texture." Wired both up
using the exact mechanisms already proven correct elsewhere in this file
-- got real, valid texture data into the pipeline for both -- but NEITHER
produces visible texture detail on screen. This section is a full record
of what was tried and what was learned, because the actual blocker turned
out to be much deeper than "wire up a texture pointer."

WHAT WAS BUILT:
- emit_model_object gained a `texptr` parameter. Each record it creates
  now publishes through g_tile_texptr_emit[rec] (the same side-channel
  array every other texture consumer in this file already uses to work
  around the in-record field truncating a 64-bit pointer to 4 bytes) --
  texptr==0 keeps the old flat-shaded fallback unchanged.
- LEAF (door): reused the closed-door billboard branch's own already-
  correct sprite frame formula, `DAT_00202734 + (raw_type_word & 7) +
  0x30`, fed through FUN_00040770 (the same real sprite decoder the 2D
  billboard path uses) to decode it, then captured the resulting buffer
  from g_tile_texptr_emit[DAT_0023b83c] right after the call (rather than
  relying on index timing) so it could be stamped onto every record the
  leaf's several faces create, not just one.
- FRAME (door): found the tile's OWN real wall-texture index by reading
  DAT_0023b4ec[2] & 0x3f (DAT_0023b4ec is the raw tile record currently
  being walked; this exact field is documented a few hundred lines above
  emit_tile_objects, in the tile-wall-rendering code itself: "UW1 tile
  word2 (bytes 2-3) bits 0-5 = wall texture index"), added 0x3a (the same
  offset that same wall-rendering code adds before calling
  get_texture_page() for the 16x16 wall-sized arena slot specifically, as
  opposed to the unmodified value used for the 64x64 floor/ceiling case),
  and called get_texture_page() with it -- the identical call the real
  wall renderer makes for this exact tile.

BOTH TEXTURE POINTERS ARE GENUINELY VALID. Added a debug pixel-histogram
check (same technique the critter sprite decoder's own UW_DEBUG_CRITTER
hook already used) -- the leaf's decoded sprite came back 1408/2048
nonzero pixels, a real 32x64 door graphic, not garbage or an empty
buffer. The frame's wall texture pointer resolved to a real, non-null
get_texture_page() result too.

RESULT: applying the leaf's sprite texture made the leaf DISAPPEAR
entirely (worse than flat-shaded) -- consistent with object-rendering-
findings.txt's own much older "LAST GAP" finding (top of this file, from
the original 2D sprite-billboard work): render_visible_tile_list derives
each vertex's texture-sample coordinate from its PROJECTED SCREEN
POSITION (near_clip_visible_tiles, offsets +0x3008/+0x300c off a per-
vertex projected-coordinate cache), not a real per-vertex UV. That
happens to look fine for a large, continuously-tiling WALL texture
(screen position lands somewhere valid no matter what), but a small
finite sprite bitmap mostly samples outside its own bounds -> reads as
transparent -> the whole leaf vanishes. This is the SAME root cause the
2D billboard sprite path has always had, just newly confirmed to affect
3D models too, since they ride the identical rendering pipeline. Reverted
to opt-in only (UW_MODEL_LEAF_TEXTURE=1); default stays untextured
(unchanged from before this session's texture work).

Applying the frame's wall texture did NOT make it disappear (a wall
texture is large enough that screen-position sampling always lands
somewhere valid) -- but it also didn't show any real texture DETAIL: a
zoomed crop of the rendered header and leaf both show perfectly flat,
uniform color, no brick/stone graining at all, before and after the
texture was applied. Chased one specific lead: real wall-rendering code
(uw.c ~49025-49032, literally the block right before emit_tile_objects
in this same function) writes the texture's tile size (DAT_0023b824 --
16 for walls, 64 for floor/ceiling) into two record fields (rb+0x0,
rb+0x4) that emit_model_object was unconditionally zeroing. Fixed that
(now writes 16 for any textured record) -- no visible change. Went one
step further and read the SAME wall-rendering code's actual raw-VERTEX
writes (uw.c ~49048-49060) expecting to confirm the vertex's 2nd/3rd
float fields are plain world Y/Z (what emit_model_object assumes and
what already works correctly for position) -- they are NOT, for walls:
those fields are computed as `Ordinal_2032((position + DAT_00086bb0/
bb1[wall_segment_index]) * 0x100)`, blending the position with a texture-
repeat lookup table indexed by which wall segment this is. Wall geometry
has its OWN specialized vertex-encoding scheme with texture-tiling baked
directly into the position fields via that table -- it is not a generic
"any 3D triangle can be textured this way" mechanism, and does not appear
to generalize to arbitrary-oriented model geometry (which needs its raw
X/Y/Z to stay literal world coordinates for POSITION to keep working,
which it does, confirmed by every model screenshot in this file).

CONCLUSION: texturing arbitrary 3D model geometry in this renderer is a
substantially deeper problem than "find the right texture pointer and
publish it" -- every existing texture consumer in this codebase (tile
walls, floor/ceiling, 2D object billboards) is tightly special-cased to
its own geometry shape, and none of those special cases were built to
generalize. Solving it for real would mean reverse-engineering how
near_clip_visible_tiles' projected-coordinate cache (+0x3008/+0x300c)
actually turns into a texture sample for the RASTERIZER'S span-drawing
code (not yet traced this session), likely requiring either a genuinely
new per-vertex UV field nothing currently writes, or replicating wall
geometry's position/texture-blending trick for a rotated model (which
doesn't obviously make sense for non-axis-aligned surfaces). This is
project-sized work on the same order as the original "get 3D models
rendering at all" investigation, not a small follow-up -- flagging
clearly rather than continuing to guess-and-check further this session.

CURRENT STATE: the frame's wall-texture wiring is left ACTIVE (harmless
-- visually identical to the untextured flat-shade fallback it already
had, and the plumbing -- g_tile_texptr_emit publishing, the texsize
field fix -- is real, correct infrastructure worth keeping even though
it doesn't yet produce a visible result). The leaf's sprite-texture
wiring is left build-time-present but OPT-IN via UW_MODEL_LEAF_
TEXTURE=1 (default off), because applying it actively regresses (leaf
disappears) rather than merely failing to improve.

UPDATE 2026-09-11 (7): THE .E PARSER COMPUTES A REAL FACE NORMAL -- AND THROWS IT AWAY
═══════════════════════════════════════════════════════════════════════════
Traced parse_e_model_file (was FUN_00020a74) end to end looking for
per-face normal data, prompted by the texturing dead-end above. Right
after reading each PARTS entry's vertex-index list, the parser calls:

    vec3_sub(P[v0], P[v1], edge1);    // was FUN_000137c0
    vec3_sub(P[v0], P[v2], edge2);
    vec3_cross(edge2, edge1, normal); // was FUN_00013904, real cross product

confirmed via the exact formula each helper computes (vec3_sub =
elementwise param_2-param_1; vec3_cross = the textbook 3-float cross
product, including the Y term's required sign flip) -- a genuine,
deliberate per-face normal computation, not a coincidence.

That result is never referenced again anywhere in the function. To rule
out a dropped-store decompile bug (this project's most common bug class),
pulled the REAL ARM disassembly from UU.exe at the call site
(0x00021aa4): `bl 0x00013904` is immediately followed by unrelated
vertex-count bookkeeping (`ldr r3,[sp,#0x38]; cmp r3,#0x4...`), no store
of the result anywhere in between. This is the real shipped binary, not
a decompile artifact -- the original game computes this normal and then
genuinely never uses it. There is no per-face normal data anywhere in
the final parsed model buffer emit_model_object reads from.

Separately confirmed while in there: the existing shading pipeline has
no per-face-normal concept to plug one into anyway -- every writer of the
render record's shade byte across this whole file (tile walls, floors,
doors, signs, emit_model_object) pulls from one shared ambient/light-
proximity global (DAT_000da47c), never anything geometry-derived. Real
per-face lighting variation would be new behavior, not a gap-fill.

UPDATE 2026-09-11 (8): NO UV DATA EITHER -- THE FORMAT WAS NEVER TEXTURE-MAPPED
═══════════════════════════════════════════════════════════════════════════
Same investigation, extended to UV/texture coordinates (the direct
follow-up to UPDATE (6)'s texturing dead-end). Read the rest of
parse_e_model_file (PARTS through EXTENDED_COLORS/CLUSTERS/NODES/ANIMATE
and its final cleanup pass) end to end. Conclusion: no UV data exists
anywhere, in the file format or the parser -- more clear-cut than the
normal, which was at least computed.

- The .E format's only blocks, across every model file in DATA3D/: BEGIN/
  VERSION/NAMES/POINTS/PARTS/CLUSTERS/NODES/EXTENDED_COLORS/SCALE_SHIFT/
  END. No UV/TEXCOORD/MAPPING block anywhere.
- Each PARTS line has exactly 4 header fields before the vertex-index
  list: a flag (always 0 in every real file -- a `local_23c==4` "got
  bitmap" branch exists for a nonzero flag but is dead in practice),
  a 1-character code, a sequential part index, and a color value. No room
  for texture coordinates. The 1-character code is NOT UV-related either
  -- confirmed via the parser's own debug string: 'A' triggers a "making
  backside of %d %d" branch that duplicates a face with reversed winding
  (a double-sided-face flag), 'N' is the ordinary default. ('F'/'X' are
  two more recognized codes seen earlier in the function, for reversed
  vertex order and an unused "explicit bitmap" escape hatch respectively
  -- also not UV.)
- Went further than the normal check: even per-face COLOR -- both the raw
  hex material index and the EXTENDED_COLORS RGB entry (matched against
  g_model_known_ext_colors, was DAT_00084678, a 32-entry known-RGB table)
  -- suffers the identical fate as the normal. Traced the function's
  literal last operation before it returns (a scratch-to-scratch color-
  inheritance pass for parts that share a color with another part,
  gated by DAT_000db494) -- it writes back into scratch memory, never
  into the final output buffer. The only things that survive into what

═══════════════════════════════════════════════════════════════════════════
Question raised by the user: since we're now leaning on uw1-decomp's
recovered bank 0x61 bytecode (extracted from the *DOS* UW.EXE) to drive
the new interpreter above, does our own WinCE UU.exe perhaps also carry
baked display-list geometry directly -- as data, even if nothing in the
compiled code reads it -- which would let us calibrate natively instead
of reconciling two independently-extracted, possibly differently-scaled
sources?

This is distinct from the original Mystery 1 finding (no *code* consumes
baked model data -- confirmed earlier via a whole-binary Ghidra xref
search across all 29 .E-loaded buffer addresses, zero consumers, plus a
full .text undefined-byte-gap scan finding no room for a hidden reader
function). That proved the *code* doesn't use it. It left open whether
the *data* might still be sitting in the binary unused.

FIRST PASS (naive, real UU.exe file: "Ultima Underworld PPC cabs
2/UWDATA/UU.exe", 882176 bytes): scanned every 16-bit LE word position
with a 512-word sliding window, counting matches against the ~44-value
uw1_dlist opcode set, looking for high-density clusters. Top hit:
384/512 words matched at byte offset 0x8ddc0. On inspection this was a
FALSE POSITIVE: a repetitive fixed-stride unrelated table (pattern
`0000 0000 0000 0001 0412 0000 XXXX 0000`, XXXX incrementing by 0x10 per
row), immediately followed by a literal embedded RIFF/WAVE/fmt audio
resource at 0x8e480. The heuristic's flaw: several real opcode values
(0x0000, 0x0002, etc.) are small integers that also occur constantly in
ordinary data by pure chance, so raw density is not distinctive.

SECOND PASS (structural, the real test): reused the *exact* opcode/
length table this project's own uwdl interpreter uses
(g_uwdl_lengths[]/uwdl_record_length in uw.c) and, for every word
position in the file, walked a chain: is this word a known opcode? does
its declared length (fixed, or base+stride*count for counted opcodes,
with the count word range-checked to 1..0x800 exactly as the real
interpreter does) land on another valid opcode? repeat. A real bytecode
stream produces long chains (bank 0x61 alone is 259 words / dozens of
consecutive records); random data hitting one of ~44 sparse opcode
values by chance should almost never chain more than 2-3 steps.

Sanity check: re-ran the scanner against the first pass's false-positive
region (0x8ddc0) -- correctly rejected, chain length 1.

RESULT across the entire 882176-byte file (441088 word positions):
maximum chain length found anywhere = 5. Full distribution: 43849
positions chain exactly 1 step, 3671 chain 2, 290 chain 3, 27 chain 4,
only 5 positions reach chain 5, and 393245 positions (89%) don't even
form one valid record. This is precisely the shape random noise produces
against a sparse opcode table -- nothing remotely resembling a real
multi-hundred-word bank exists anywhere in the file.

CONCLUSION: UU.exe contains no baked display-list/bank geometry data
anywhere, matching (and now strengthening) the original Mystery 1
finding. Combined with the earlier proof that no code path reads such
data either, this closes the question completely: this WinCE port's
compiled binary never had display-list geometry, as code or as data.
The uw1-decomp DOS-side bank data (already embedded for bank 0x61 above)
and this project's own .E files remain the only two available sources
of real 3D geometry -- there is no third, WinCE-native source to fall
back on for calibration. The vertex-drop bug in uwdl_face_vertex
(confirmed 28/288, 9.7%, dropped for bank 0x61 -- see next update) stays
the active blocker for a clean door-frame render.

UPDATE 2026-09-17 (2): ROOT-CAUSED AND FIXED THE VERTEX-DROP BUG --
REAL, CLEAN DOOR-FRAME GEOMETRY NOW RENDERS
═══════════════════════════════════════════════════════════════════════════
Root cause: uwdl_face_vertex, when a face opcode (0x007e/0x00a8/0x00b4/
0x00ce) referenced a slot the interpreter's walk never marked `placed`
(a corner only some *other* branch policy fills in), silently dropped
that vertex from the face's vertex array and shifted the rest down to
fill the gap. A would-be quad missing corner 2, say, became a 3-vertex
face made of corners {0,1,3} -- structurally a different, wrongly-wound
polygon, not a smaller honest one. This is what produced the banded,
discontinuous fragment in the prior update.

Checked uw1-decomp's own face_vertex (port/uw1_dlist.c:484-501) for how
the real implementation handles this -- it does NOT drop anything:

    static void face_vertex(vm *m, uw1_dlist_face *f, uint16_t off)
    {
        slotv *s;
        if (f->count >= UW1_DLIST_FACE_VERTS) { m->out->overflow = 1; return; }
        s = slot_at(m, off);
        f->slot[f->count] = off;
        f->placed[f->count] = (s != NULL && s->placed);
        if (s != NULL && s->placed) {
            f->p[f->count][0] = s->p[0]; f->p[f->count][1] = s->p[1];
            f->p[f->count][2] = s->p[2];
        }
        f->count++;
    }

Every vertex reference is always appended, always incrementing count; an
unplaced one just carries placed=0 (and p left at zero). The DOS
*interpreter* never discards anything. The discarding happens one layer
up, in the actual consumers -- uw1_view_door_faces and
uw1_view_model_faces (port/uw1_view.c:2643-2691, 2762-2781) -- and it's
a whole-face decision, not a per-vertex one:

    if (f->count != 4) { continue; }        /* nothing either bank builds */
    ...
    for (j = 0; j < 4; j++) {
        if (!f->placed[j]) { break; }        /* a corner the run never placed */
        ... build o->p[j] ...
    }
    if (j == 4) { n++; }                     /* only a fully-placed quad counts */

So a face is either a complete, fully-placed quad (drawn) or it's
thrown away whole (not drawn, not patched, not reconnected). Given the
branch-union algorithm already ported in UPDATE 2026-09-16 (3) explores
every distinct declined/taken policy and unions the resulting faces by
identity, a corner that's unplaced under one policy is expected to come
back fully placed under a different policy's run -- the "whole face or
nothing" rule is what makes that algorithm correct; salvaging partial
faces (what this port's code was doing) fights against it instead.

FIX applied in uw.c:
  1. Added `int placed[UWDL_MAX_FACE_VERTS];` to the `uwdl_face` struct.
  2. `uwdl_face_vertex`: always appends now (removed the drop/reindex
     branch); stores `placed[i]` and zeroes p[i] when unplaced, exactly
     matching face_vertex above. g_uwdl_vertex_attempted/dropped kept as
     diagnostic counters (renamed the debug message from "DROPPED" to
     "unplaced" since it's no longer discarded from the face).
  3. `uwdl_same_face`: now compares `placed[i]` per-vertex and only
     compares p[i] when placed, matching DOS's own same_face
     (port/uw1_dlist.c:415-448) -- needed so face-identity dedup across
     branch-policy runs works the same way DOS's does.
  4. `emit_dlist_bank_object`: added the exact whole-face filter from
     uw1_view_door_faces/uw1_view_model_faces -- skip any face where
     count != 4, or any of the 4 vertices has placed == 0. (Scoped to
     this exact call site/bank family, which is the only thing this
     function currently serves and the only thing the DOS source cited
     above actually proves this rule for.)

RESULT: bank 0x61 now decodes to 11 real faces (was 9 before the fix --
the dedup identity changed because corrupted partial faces are no
longer counted as distinct "faces" to compare against). Re-tested at a
real door (tile 24.5,6.5, heading 270, the same repro used throughout
this investigation) with UW_DLIST_DOOR=1 UW_DLIST_DOOR_TEXTURE=1
UW_DLIST_DOOR_ONLY=1 UW_DLIST_HEADING_OFFSET=-3 UW_DLIST_YOFF=0 (the
door leaf hidden so only the interpreter's own output is visible):
pixel diff against the same shot with UW_DLIST_DOOR unset went from
UPDATE 2026-09-16 (3)'s 140 scattered pixels to 7028 pixels in one
coherent 90x106 bounding box -- and visually (see
scratchpad screenshots from this session; crop of the doorway region)
it is now a clean, recognizable, correctly-shaped rectangular doorway
opening with real stone-wall texture across the frame, not a banded
fragment. This is the first result in this investigation that actually
looks like a door frame rather than "proof the mechanism runs."

Vertex-drop counters still report attempted=288/dropped=28 per run
(same numbers as before -- the interpreter still visits the same
slots), but "dropped" now means "counted as unplaced, correctly
excluded its whole face" rather than "silently corrupted a face that
then got drawn anyway." Not yet fully calibrated (heading offset -3 and
yoff 0 are still the best-found values, not independently re-derived
for this exact fix), but the structural bug that was actively fighting
any calibration attempt is gone.

UPDATE 2026-09-18: TWO TEXTURE-SAMPLING BUGS FOUND AND FIXED -- "EVERY
OTHER COLUMN TRANSPARENT"
═══════════════════════════════════════════════════════════════════════════
User report, testing the previous update's clean door-frame render: the
new textured path draws every other column (of the real 320x240
framebuffer) as transparent. Investigated by reading the actual
rasterizer (raster_triangle/raster_textured_span, uw.c ~6963-7531) this
project already has, rather than guessing -- both bugs found and fixed
are real, cited defects in this session's own emit_dlist_bank_object
code, not pre-existing engine bugs.

BUG 1 -- wrong texture-stride field (ace00/ace04).
raster_textured_span's per-pixel texel address computation
(uw.c ~7490-7502) is:

    do {
        iVar6 = Ordinal_2005(local_38, 0x1000000);         /* perspective divide */
        iVar12 = (local_34 >> 6) * iVar6 >> 0x12;           /* "row" (V) index */
        bVar1 = param_10;
        if ((param_8 != 0) && (-1 < iVar12)) {
            for (iVar12 = iVar12*param_6 + ((iVar14>>6)*iVar6>>0x12);
                 param_7 < iVar12; iVar12 = iVar12 - param_7) { }
            bVar1 = *(byte *)(iVar12 + param_8);            /* the real texel fetch */
        }
        ...
    } while (...)

param_6/param_7 (the row stride and the wraparound-total) come straight
from the arena's per-face `ace00`/`ace04` fields (render_visible_tile_list,
uw.c ~13701-13706: `raster_triangle(0x140, fb, tri, tex, piVar14[0x1b],
piVar14[0x1c]*piVar14[0x1b], texptr, rect)` -- piVar14[0x1b]/[0x1c] trace
straight back to those two fields). The REAL tile-wall render path (uw.c
~50276-50277 and ~50523-50524, gated by the exact same LOD/distance
check, `DAT_00086b24`) writes the texture's actual pixel width there --
0x40 (64) for the near/real-detail branch, 0x20 or 0x10 for the
LOD-reduced branches -- for the exact same wall-texture-index expression
(`(byte)DAT_0023b4ec[2] & 0x3f`) the door path already reuses to resolve
its own texture. This session's dlist code instead hardcoded this field
to a placeholder `16` regardless of what was actually bound (a leftover
from the UPDATE 2026-09-16 (3) "use texsize" experiment, before UV
scaling was later split out into its own independent constant -- this
field was never revisited afterward). Binding a real 64-pixel-wide
texture (index 24, confirmed via `get_texture_page`) while telling the
rasterizer its pitch is 16 makes the wraparound math run on completely
the wrong stride against the real 4096-byte buffer.

FIX: added `uwdl_texture_width(int idx)`, a direct port of
`get_texture_page`'s own size classification (idx<0x30 -> 64, <0x3a ->
32, <=0x73 -> 16, else 0 -- uw.c ~31174-31196), and threaded a real
`texwidth` parameter through `emit_dlist_bank_object` (previously
implicit/hardcoded) so the ace00/ace04 write and the UV scale (next bug)
both use the one real value for whichever texture is actually bound.

BUG 2 -- UV words are signed, and DOS's own bytecode legitimately
produces small negative/near-zero UV.
Checked `uw1-decomp/port/uw1_dlist.c` directly (not assumed): its own
`sign16()` is applied to face UV words too (lines 651-652, 664-665),
exactly matching this project's `uwdl_sign16`. So this part was already
a faithful port -- a raw word `0xffff` really does mean `-1`, not
`65535`, on both sides. Dumping bank 0x61's real per-face UV (new
`UW_DEBUG_DLIST_UV=1` flag) confirmed real corners like:

    face 6: u=(0,16383,16383,0) v=(12288,12288,-1,-1)
    face 7: u=(-16384,-1,-1,-16384) v=(12288,12288,-1,-1)

-1 and -16384 are small, sane values once scaled (uscale = 64/65536 ~=
0.000977 -- -16384*uscale = -16.0, a texel or two off one edge, not a
huge swing). The actual failure mechanism is the rasterizer's own
boundary check above: `if ((param_8 != 0) && (-1 < iVar12))` gates the
texel fetch on the interpolated V accumulator being >= 0. A per-vertex V
sitting at or barely below zero (our v=-1 corners, or any face whose
whole V range straddles zero after scaling) puts every scanline's
interpolated V right on that knife-edge; fixed-point rounding and the
perspective divide (`Ordinal_2005`) flip it across zero from one pixel
to the next, so the fetch alternately passes and fails -- exactly the
reported checkerboard. Real tile walls never hit this edge case because
their own UV is always constructed >= 0 (tile-local offsets, never
negative) -- this port's raster function may simply never have been
exercised with negative UV before now.

FIX: in `emit_dlist_bank_object`, before scaling a face's UV to pixel
units, compute the face's own minimum u and v (across whichever 4
source vertices that face's fan-triangulated quad actually uses) and
subtract it from all 4 corners first. This is a pure additive rephase
of a tiling texture -- the face's own relative UV shape (what actually
determines the visible texture placement/gradient across that quad) is
completely unchanged, it just guarantees every sample for that face
lands comfortably on the valid (>=0) side of the rasterizer's boundary
check instead of straddling it.

(door at tile 24.5,6.5, heading 270, UW_DLIST_DOOR=1
UW_DLIST_DOOR_TEXTURE=1 UW_DLIST_DOOR_ONLY=1). Before the fix, a

draws, only whether previously-corrupted pixels within that same region

UPDATE 2026-09-20: THE REAL ROOT CAUSE -- ARENA UV FIELDS HOLD A PLAIN
TRUNCATED INT, NOT A FLOAT BIT PATTERN. STANDING RIGHT IN FRONT OF A
DOOR SHOWED THIS WAS STILL BROKEN (RANDOM STATIC), NOT JUST MISCALIBRATED
═══════════════════════════════════════════════════════════════════════════
User report, testing UPDATE 8/9's fixes live: standing right in front of
a door frame (not a few tiles back, where every previous screenshot in
this investigation was taken) showed high-frequency salt-and-pepper
static across the whole textured surface -- visually nothing like a
column or row gap pattern, more like reading garbage/noise. This was a
real, different, worse bug that every prior screenshot (taken from
further away, where the artifact is much less visible) had missed --
a real gap in this investigation's own verification standard, now
corrected by testing close-up specifically.

METHOD: rather than guess again, instrumented the actual consumer --
raster_textured_span (uw.c ~7490-7539) -- with a new UW_DEBUG_RASTER_UV
flag that logs, per rasterized span touching our door's texture pointer,
the per-pixel V step (`*(int*)(param_3+0x44)`) and the resulting min/max
interpolated value and computed texel address. Live result before this
fix: `vstep(0x44)=-1904738304` -- close to two BILLION per pixel -- and
`local_34` swinging from roughly -1.8 billion to +2.1 billion within a
single few-pixel scanline span, with the resulting texel address landing
uncorrelated all over the 0..4095 valid range pixel to pixel. That's
exactly what "random static" looks like: the interpolator is walking a
value so enormous relative to its useful range that only noise-like low
bits survive into the final address.

ROOT CAUSE: traced where that per-pixel step comes from --
raster_triangle_perspective_setup (uw.c ~7162+) builds it from a 3-vertex
`x,y,w,u,v` array (`render_visible_tile_list`'s own comment at uw.c
~13630-13636 confirms this layout explicitly), and that array's u/v
entries are populated by `Ordinal_2032(piVar14[0x10])` /
`Ordinal_2032(piVar14[0x11])` -- Ordinal_2032 is int->float (uw.c
ordinal_stubs.c:980-984, confirmed by reading the real implementation
directly, not guessed): it takes a plain C int and produces the IEEE
bit pattern for that integer's *value*. piVar14[0x10/0x11] are read as
plain ints here.

Cross-checked against the real, working wall-populate code's own last
step for this same field (uw.c ~50356-50360):

    uVar20 = Ordinal_2015(0x44800000, Z);      /* 1024.0 - Z (softfloat SUBTRACT) */
    uVar20 = Ordinal_2026(uVar20, 0x3b800000); /* * (1/256) */
    Ordinal_2026(uVar20, uVar17);              /* * (texsize-1) */
    uVar20 = Ordinal_2020();                   /* !! */
    (&DAT_000ace0c)[iVar18] = (char)uVar20;

`Ordinal_2020(x)` (ordinal_stubs.c:897-901) is
`(long)ordfloat_bits_to_float(x)` -- NOT a bit-reinterpret. It converts
the float BITS in `x` into a real C `float` VALUE, then casts that
*value* to a `long` (a genuine truncating numeric conversion, e.g.
50.7f -> 50). So the wall path's own last step deliberately converts its
computed float back down to a plain truncated integer before storing it
-- the arena's ace0c/ace14/ace1c/ace24 fields hold a plain int the whole
time, and `Ordinal_2032` on the read side (render_visible_tile_list)
converts that plain int into a float for the one-time perspective-setup
math. A clean, consistent int<->float round trip on the real path.

This session's dlist code instead wrote `*(float *)(&DAT_000ace0c + rb)
= (float)v;` -- a raw C float bit pattern, not a truncated int. When
`Ordinal_2032` on the read side treated that bit pattern as a plain
integer and converted THAT integer's value to float, a modest V value
like 50.0f (bit pattern 0x42480000 = 1,111,490,560 as a plain integer)
became int->float(1111490560) ~= 1.1114906e9 -- almost exactly the ~1.9
billion magnitude the live instrumentation caught. Every previous
UV-related fix in this investigation (the stride fix, both UV-rephasing
attempts, and the switch to the wall's U=0/V=height convention) was
built on top of this same float-instead-of-int storage mistake, which
is why every attempt still produced *some* kind of visible corruption --
the actual values being interpolated were never sane to begin with.

FIX: changed the UV write in emit_dlist_bank_object to store a plain
`int32_t` (matching Ordinal_2020's real truncating contract) instead of
a `float` cast, for all 4 corners' U and V.

VERIFICATION: re-ran the same UW_DEBUG_RASTER_UV instrumentation at the
exact door the user was standing in front of
(SETPLAYERPOS 33.23 8.68 640 101 7, from the user's own manual-test
session log). Per-pixel V step dropped from -1904738304 to -15380 --
five orders of magnitude smaller, a small sane increment -- and the
computed texel addresses now vary smoothly and coherently within the
valid 0..4095 range across each span (e.g. 3840->3968, 3712->3840),
instead of jumping randomly. Visually: the random static is completely
gone, replaced by a coherent, correctly-sampled textured surface on both
door-frame jambs. Not yet perfectly calibrated -- the visible texture
repeats noticeably more densely (more/thinner horizontal bands) than a
real wall's own texture density, suggesting the V magnitude, while no
longer catastrophically wrong, likely still needs the same kind of
scale-down the wall formula applies (the `(1024-Z)/256` term) rather
than raw world-height units -- but this is an ordinary calibration
question now, not corruption. Confirmed via the standard demo.txt
regression script: no crashes.

The new UW_DEBUG_RASTER_UV instrumentation is left in place (gated,
off by default) since it was the difference between guessing and
actually finding this bug -- worth keeping for the next texture issue.

UPDATE 2026-09-20 (2): U=0 WAS THE WRONG GENERALIZATION -- REAL DOOR
FRAME TEXTURE NOW WORKS IN BOTH AXES
═══════════════════════════════════════════════════════════════════════════
User report after the int/float fix: vertical (V) looked right, but the
frame looked like a single texture column stretched across the whole
X width. Root cause was UPDATE 9's own change: it set U unconditionally
to 0, generalized from grepping every real wall-populate site in this
file (all of which really do write literal 0 there). That grep was
correct about what those sites write, but the generalization drawn from
it -- "this renderer never varies U, ever" -- was wrong for this case.

Why U=0 works for walls: raster_triangle_perspective_setup builds a
perspective-corrected U gradient from the *3 triangle vertices'* own U
values; if a wall's own quad only ever covers about one texel-column's
worth of real-world horizontal extent (many narrow quads side by side
making up a full wall, not one wide quad), sampling texel-column 0 for
that whole narrow sliver is locally correct, and the next quad over
covers the next texel column the same way, etc -- horizontal texture
variation across a wide wall comes from many quads, not one.

This bank's own faces are not built that way: bank 0x61's own bbox is
x=[-112,144] (256 world units, several texture repeats) in a single
quad per face, not many narrow ones. U=0 the whole time meant every
pixel across that whole 256-unit-wide quad sampled the exact same
texel column -- precisely "one texel stretched across X."

FIX: varies U the same way V already does (UPDATE 8/9's approach,
now correctly stored as a plain int per UPDATE 10) -- from each
vertex's own real position, normalized per-face to a non-negative
minimum. Specifically each vertex's local X (f->p[.][0], the
PRE-rotation local coordinate, same role local Y already plays for V):
this bank's own geometry is thin in Z (bbox z=[0,8], the frame's own
wall thickness) and wide in X, so X is the real "width" axis for this

UPDATE 2026-09-20 (2): MISSING GEOMETRY -- WE NEVER SEEDED THE "RISE"
ORIGIN SLOT DOS's PROLOGUE ALWAYS SETS UP FOR BANK 0x61
═══════════════════════════════════════════════════════════════════════════
User report: door frame scaling/positioning looks off against the DOS
reference. Re-read uw1-decomp's door_model (port/uw1_view.c ~2528-2586)
line by line instead of re-deriving from memory, and found something
this investigation's earlier UV-focused sessions had missed entirely:
DOS never runs a bank's bytecode raw. `door_model` always synthesizes
an 8-word prologue in front of the real bank and CALLS into the bank
through it:

    region[p+0] = 0x004c;             /* store, no translate */
    region[p+1..3] = 0, 0, rise;      /* (x, z, y) = (0, 0, rise) */
    region[p+4] = 0x0800;             /* destination: slot 0x800 */
    region[p+5] = 0x0012;             /* call */
    region[p+6] = <displacement to the real bank's own head>;
    region[p+7] = 0x0000;             /* end, after the call returns */

`rise = UW1_VIEW_DOOR_LINTEL_TOP - org[2]` (LINTEL_TOP = 0x330 = 816,
confirmed straight from uw1_view.h:1467; org[2] is the door object's own
world height, the same value that later becomes `o->p[j][2] = org[2] +
y` -- this renderer's `ah`/DAT_0023b91c anchor component).

Checked whether this is just academic bookkeeping or whether bank
0x61's own bytecode actually reads slot 0x800 -- it does, four times:

    0x008c 0x0060 0x0800 0x0080   (vertex_sum: dest 0x80 = slot 0x60 + slot 0x800)
    0x008c 0x0068 0x0800 0x0088
    0x008c 0x0070 0x0800 0x0090
    0x008c 0x0078 0x0800 0x0098

`K_VERTEX_SUM`'s own real behavior (uw1_dlist.c ~577-585): `if (a ==
NULL || b == NULL || !a->placed || !b->placed) return;` -- it refuses
to store anything if EITHER source is unplaced. This interpreter's own
`uwdl_run_bank` never seeded slot 0x800 (index 256 of 257 -- confirmed
UW1_DLIST_SLOTS/UW1_DLIST_SLOT_STRIDE are 257/8, identical to this
port's own UWDL_SLOTS/UWDL_SLOT_STRIDE), so it was permanently
unplaced, all 4 of those vertex_sum destinations were permanently
unplaced too, and -- combined with the earlier fix requiring a face's
4 corners to ALL be placed to draw at all -- every face that
transitively depended on any of those 4 slots was silently dropped.
This wasn't a coordinate-offset bug, it was missing geometry: real
faces (the lintel top, going by the slot naming and LINTEL_TOP's own
name) were never being built at all.

FIX: added a `rise` parameter to `uwdl_run_bank`, computed in
`emit_dlist_bank_object` as `0x330 - ah` (the exact DOS formula, using
this renderer's own height anchor in place of DOS's org[2]), and seed
slot 0x800 with (0, 0, rise) at the start of every branch-exploration
pass (matching DOS's prologue being applied once per real `door_model`
call, replicated once per pass here since each pass resets the whole
slot table). Axis-checked against this interpreter's own `uwdl_place`
(`p[0]=x, p[1]=y, p[2]=z`) to put `rise` in the right slot (p[1]).

slots attempted=288 dropped=28, bbox y=[0,208]. After: attempted=288

UPDATE 2026-09-20 (3): UV SCALE WAS 1:1 RAW WORLD UNITS -- SHOULD BE

═════════════════════════════════════════════════════════════════════════════

gotten U/V's *storage type* and *non-negativity* right but never
revisited their actual magnitude -- U and V were raw world-unit position
deltas, scaled by exactly 1.0 (1 world unit = 1 texel).

Went back to the real wall-populate V formula traced when root-causing
the earlier float-vs-int static bug (uw.c, the wall-tile-face code):

    V = ((1024.0 - height) / 256.0) * (texwidth - 1)

magnitude (~4x smaller) matches the user's own "3-4x too dense" report
almost exactly.

UPDATE 2026-09-20 (12): THE REAL BUG -- ace04 USED texwidth INSTEAD OF

═══════════════════════════════════════════════════════════════════════════

Checked both hypotheses against real data instead of guessing:
- Added a new UW_DEBUG_DLIST_FINALUV flag dumping the actual computed
  u0..v3 int values written per face. For the leaf's real textured
  face: u=(0,32,32,0) v=(0,0,64,64) -- the full 0..32/0..64 corner
  range IS being written correctly. Not a UV-assignment bug.
- Independently verified the sprite's real dimensions straight from the
  DOORS.GR resource file on disk (not just trusting FUN_00040770's own
  self-report): its own header format (byte0=compression mode, byte1=
  width, byte2=height) shows the first entry's real header bytes as
  `04 20 40 00` -- mode 4 (raw), width 0x20=32, height 0x40=64. Matches
  FUN_00040770's own decode exactly. Not a wrong-height-source bug
  either.

Found the real cause with the existing UW_DEBUG_RASTER_UV instrumentation
instead: `total=1024` for the leaf's texture calls -- but a 32x64 sprite
is 2048 bytes, and `total` (param_7 in raster_textured_span) is the
modulus the row/column address wraps at. 1024 = 32*32, not 32*64 --
exactly half. Traced to `emit_dlist_bank_object`'s own ace00/ace04
write: `ace00 = texwidth; ace04 = texwidth;` -- BOTH fields getting the
same value. This is correct for every real WALL texture this file uses
(they're always square, 16x16/32x32/64x64, so width==height and the
coincidence was invisible), but ace04 is NOT "width again" -- it's the
field render_visible_tile_list multiplies by ace00 to get the real
wraparound total (`param_7 = piVar14[0x1c] * piVar14[0x1b]`), i.e. the
image's real HEIGHT term, not its width. For the leaf's genuinely
rectangular 32x64 sprite this silently computed 32*32=1024 instead of
32*64=2048, and raster_textured_span's own wraparound
(`for (...; param_7 < iVar12; iVar12 -= param_7)`) folded every row
address past 32 back into the TOP half of the buffer -- the bottom half
of the sprite was mathematically unreachable, not merely under-scaled.
This is exactly "a small piece of the door, not the full height," and
it's also exactly a sprite-dimension bug in effect (half the real
height silently discarded) even though the SOURCE dimensions were read
correctly -- both of the user's hypotheses were pointing at the same
real defect from two different angles.

FIX: `ace04 = texptr ? texheight : 0;` instead of reusing texwidth. No
effect on the frame/wall path (texheight==texwidth there, passed
identically at both frame call sites already).

VERIFICATION: UW_DEBUG_RASTER_UV now reports `total=2048` for the leaf
(matching the real 32x64=2048-byte buffer exactly). Screenshot at the

  - yaw=85 (quadrant=1): heading=0, world=(4320,848,688) -- world X
    also shifted by +128, a clean 1:1 mapping.
  - yaw=150 (quadrant=2): heading=6, world=(3664,848,64) -- world X
    UNCHANGED despite the same +128 local X shift.

ROOT CAUSE: xoff/zoff are added to local X/Z *before* the per-object
heading rotation (ca,sa = cos/sin(heading*45deg), already carrying the
existing -2*DAT_0023b4a0 quadrant correction). Their combined effect
on SCREEN X is exactly `ca*xoff - sa*zoff` (from rx = mx*ca - mz*sa,
mx = local_x+xoff, mz = local_z+zoff). At heading=0 (this door, one
camera quadrant): ca=1, sa=0 -- ONLY xoff affects screen X, zoff does
literally nothing. At heading=6 (the SAME real door, one camera
quadrant over -- not a different door, not a calibration difference):
ca=cos(270deg)=0, sa=sin(270deg)=-1 -- that INVERTS entirely: xoff now
does literally nothing (its whole coefficient is ca=0) and zoff
controls screen X completely instead. An xoff-only correction (zoff
defaulted to 0.0 until the previous entry) is chasing a moving target:
at some headings its entire effect lands on an axis that isn't even
being corrected. This is exactly and completely explains "the sign
needs to flip" -- it's not really a sign flip, it's the SAME fixed
local-space correction periodically landing its effect on the wrong
screen axis as heading rotates through 90-degree steps.

THE FIX: use the model's own real 2D local bias as a proper (x,z)
vector, both components together, so the correction rotates WITH the
object's own geometry and keeps canceling correctly at every heading
by construction -- rather than trying to track a screen-space
direction that doesn't stay fixed. UW_DEBUG_DLIST's own bbox print
already had this measured on BOTH axes, not just X (previous entries
only used the X half of it): bank 0x61 (frame) bbox x=[-112,144]
z=[0,8], bank 0x6e (leaf) bbox x=[-48,80] z=[0,8] -- both banks center
at exactly (+16,+4), not (+16,0). Changed BOTH defaults: xoff=-16.0
(back up from -8.0), zoff=-4.0 (new, was 0.0).

VERIFICATION (mathematical, then live): with xoff=-16,zoff=-4, a
vertex at the bbox center (local x=16,z=4) has mx=mz=0 for ANY heading
-- rx=rz=0 regardless of ca/sa, so it maps EXACTLY onto the anchor
point at every possible camera quadrant, by construction, not by
per-angle tuning. Confirmed directly against real UW_DEBUG_DLIST_XFORM
output for the same two quadrants used above: at heading=0, the
frame's full local X span [-112,144] now maps to world X range
[4112,4368] -- center exactly 4240, matching the printed anchor
(4240,640,688) exactly. At heading=6, the SAME span maps to world X
range [3660,3668] -- center exactly 3664, matching the printed anchor
(3664,640,144) exactly. Both camera quadrants land exactly centered on
the anchor with the identical (xoff,zoff) pair, no sign flip anywhere,
no per-quadrant branching needed. Live screenshot at the QA3 repro
position (tile=31.95,8.98 z=640 yaw=85) confirms the door and frame
sit centered with no visible gap or wall clip. Standard
run-regressions.sh: 6/6 clean.

Note on the earlier "-16 overshoots, halved to -8" finding (UPDATE
2026-09-20 (15)): that observation was real, but it was a symptom of
testing an X-ONLY correction across multiple doors/headings before
zoff existed at all to catch the axis the correction's effect was
actually landing on at those headings -- not evidence that -16 was the
wrong X magnitude. With zoff now present and set correctly alongside
it, -16 is exactly right.

UV FLIP (point 3): confirmed to be a genuinely SEPARATE issue, not
explained or fixed by the above. Checked directly with
UW_DEBUG_DLIST_FINALUV across the same two camera quadrants (yaw=85
vs yaw=150) for the same door: the printed u0..v3 output is
byte-identical between them for every face. This has to be true given
the code as written -- the UV computation (`u0 = (f->p[s0][0]-umin)*
uscale`, etc., ~uw.c 53409-53416) reads ONLY the raw, untransformed
local bytecode coordinates (f->p[], not vf[]) and never references
heading, ca/sa, xoff, or zoff anywhere. It is mathematically
impossible for this specific computation to vary with camera angle as
currently written, camera-quadrant-dependent or not.

If the actual rendered texture still visibly flips with view angle (as
reported), the cause must be downstream of this UV computation --
almost certainly in how the shared rasterizer (raster_triangle/
raster_textured_span) associates u0..u3 with actual on-screen quad
corners, which DOES depend on the quad's final screen-space vertex
order/winding, and that winding can legitimately change as heading
rotates a quad through view-dependent front/back orientations.
Leading hypothesis, NOT YET CONFIRMED: this renderer is effectively
viewing the BACK of a single-sided textured quad at some headings (a
real, expected 3D-geometry situation, not a calibration issue) without
the rasterizer mirroring or culling for that case -- consistent with
this same document's still-open note on DAT_000db480/DAT_000db470/
DAT_000db494 (the double-sided-face/EXTENDED_COLORS gating flags,
confirmed to have no writer anywhere in this decompile, always
BSS-zero). Not fixed this round -- flagged as the next thing to chase,
independently of the now-resolved xoff/zoff fix above.
